# zengenetics-reviews — 리뷰 사이트 (review.zengenetics.co.kr)

> 목적: **리뷰 26,969건을 크롤러와 LLM 이 읽을 수 있게 만든다.**

## 왜 이게 필요한가 (2026-09-16 진단)

카페24 상품페이지의 리뷰는 **알파리뷰 JS 위젯이 로드 후 주입**한다. 원본 HTML 에는
빈 컨테이너(`<div class="alpha_widget" data-code="…">`)만 있고 리뷰 본문이 **0자**다.
Googlebot 은 JS 를 렌더하지만, **AI 답변을 만드는 크롤러 대부분은 JS 를 실행하지
않고 원본 HTML 만 읽는다.** 그래서 리뷰가 아예 안 보인다.

숫자도 틀려 있다.

| | 값 | 누가 보는가 |
|---|---|---|
| 알파리뷰 실제 보유 (칼륨) | **26,969** | 사람 |
| 페이지 JSON-LD `reviewCount` | **419** | **구글·LLM** |

원본 HTML 에서 `26969` / `26,969` 를 검색하면 **0회**다. 구글은 실제의 **1/64** 로
알고 있다. 상세페이지 본문도 이미지 14장·의미있는 `alt` 0개·한글 130자뿐이라
AI 가 인용할 문장이 사이트에 한 줄도 없다.

## 구조

```
_sync.py    리뷰 수집 → data/reviews.json (단일 스토어, id 오름차순)
_build.py   스토어 → dist/ (HTML · sitemap.xml · robots.txt · CNAME)
data/
  products.json   product_no ↔ slug ↔ 상품명
  reviews.json    리뷰 스토어. 레코드마다 진짜 소속 product_no 를 갖는다
dist/             생성 산출물 (gitignore — 워크플로가 매번 다시 만든다)
```

`.github/workflows/reviews.yml` 이 매일 **수집 → 커밋 → 생성 → Pages 배포**를 돈다.

### 단일 스토어인 이유 — 알파리뷰는 상품별로 리뷰를 분리하지 않는다

성분이 같은 상품군이 같은 리뷰 풀을 공유한다. 실측:

| 조회 대상 | 보유 건수 | 표본 60건 비교 |
|---|---|---|
| `magnesium` / `daypack-magnesium` / `set-performance` | 모두 **18,799** | **60/60 전수 일치** |
| `vitaminb` / `daypack-vitaminb` | 모두 **6,484** | **60/60 전수 일치** |
| `potassium` / `daypack-potassium` | 26,970 / 27,041 | 56/60 |
| `set-swell` | 33,631 | ≈ 칼륨 26,970 + 비타민B 6,484 |

`product_no=64`(퍼포먼스 세트)로 조회해도 실제로는 `product_no=16`(마그네슘) 리뷰가
섞여 나온다. **조회에 쓴 product_no 로 페이지를 나누면 마그네슘 리뷰가 '퍼포먼스 세트'
후기로도 게재되어 중복 콘텐츠이고 사실과도 다르다.**

다행히 API 는 리뷰마다 진짜 소속 상품을 알려준다(`product.product_no`). 그래서 전
상품을 한 스토어에 모아 id 로 중복을 제거하고, **빌더가 리뷰 자신의 product_no 로
페이지를 나눈다.** 어떤 리뷰도 두 번 게재되지 않는다.

### 페이지 경계를 고정한 이유

스토어를 id 오름차순으로 놓고 50건씩 끊는다. 신규 리뷰는 **마지막 페이지에만** 쌓이므로
기존 페이지의 URL 과 내용이 유지된다.

- 매일 재배포되는 파일이 1~2개뿐이다
- 이미 색인된 페이지 내용이 매일 뒤바뀌지 않는다 (색인 감점 회피)

대신 1페이지가 과거 리뷰가 되므로 허브(`index.html`)는 **최신 페이지를 앞에** 놓는다.

### 코퍼스의 실질 정보량 — 기대치를 낮춰 둘 것

표본 258건 측정 결과:

| | 건수 | 비율 |
|---|---|---|
| 전체 | 258 | 100% |
| 고유 본문 | 158 | — |
| **정형문구 반복분** | **129** | **50%** |
| 40자 이상 & 고유 | 61 | 23% |

알파리뷰 간편리뷰는 정형 문구를 터치 한 번으로 등록한다. 그래서
`만족스러워요! 붓기에 효과 좋아요🍀` 같은 문장이 8회씩 반복된다. **26,970건이라는
숫자에서 LLM 이 실제로 인용할 만한 문장은 20% 남짓**으로 보는 게 맞다.

그래도 20%면 5,000건 규모이고, 지금 카페24 상세페이지의 130자와는 비교가 안 된다.
정형문구도 걷어내지 않는다 — 걷어내면 **전량 게재 원칙**(아래 심의 설계)이 깨진다.

## 데이터를 어떻게 넣는가

### 1. 최초 백필 — 엑셀 내보내기 (대표님, 1회)

**알파리뷰 대시보드 → 리뷰 목록 → 우측 상단 [엑셀 다운로드]**

- 기간 **한 번에 최대 6개월** — 26,969건이면 여러 번 나눠 신청
- 처리 **평균 3~4시간**, 이메일 수신, 보관 **7일**
- 비밀번호 **10~16자 · 2종 이상 조합**. 알파리뷰가 복구해주지 않으니 반드시 기억
- 요청 후 이메일 주소 변경 불가

> ⚠️ **내보낼 컬럼은 `리뷰내용` · `평점` · `작성일` · `상품명` 만 고른다.**
> 주문자명·연락처·이메일·주문번호는 **선택하지 않는다.** 이 사이트는 공개 페이지이고
> 스토어는 공개 저장소에 커밋된다. 원본 CSV 는 `.gitignore` 로 제외된다.

```bash
python3 _sync.py --csv 알파리뷰_내보내기.csv
```

상품명으로 갈라 각 스토어에 병합한다. 매칭 실패한 상품명은 경고로 찍히니
`data/products.json` 에 추가한다.

### 2. 신규 리뷰 — 자동 (개입 0)

```bash
python3 _sync.py --api              # 전 상품 신규 (워크플로가 이걸 돈다)
```

워크플로가 매일 대신 돈다.

### 3. 임시 백필 — API 전 구간 (엑셀 오기 전까지)

```bash
python3 _sync.py --deep 11          # product_no 지정. 중단되면 재실행으로 이어진다
```

증분 모드는 상품당 페이지 예산 20장이다. 과거 이력은 이 모드나 엑셀 내보내기로 채운다.

## 위젯 API 실측 (중요 — 추측으로 고치지 말 것)

`GET review-widget.alphwidget.com/v2/api-widget` · `mall_id=wespotjo` · `shop_no=1`
· `widget_code=7ee3b8bd` (`/v2/api-widget/sets?widget_set_code=a070d8ba` 로 얻음)

### 정렬이 순수 최신순이 **아니다**

앞머리에 **고정 노출 리뷰 4건**이 붙고, 그 뒤부터 id 내림차순이 시작된다.

```
page 1 → 78633090, 75141298, 74012666
page 2 → 68037045, 99940570, 99919641   ← 여기서 최신순이 시작
```

그래서 **"아는 id 를 만나면 중단"은 틀렸다.** 고정 리뷰만 있는 page 1 에서 멈춰
신규를 영구히 놓친다. `sync_api` 는 신규가 없는 페이지가 `MISS_TOLERANCE`(3)번
연속 나올 때만 멈춘다. 이 동작은 테스트로 실증했다(2페이지 소재 리뷰를 일부러
지우고 재동기화 → 복구 확인).

### 그 외 한계

- **`page_size` 가 서버에서 3 으로 고정** — 늘려도 무시된다
- **page 500 에서 클램프** — 이진탐색 확인. page 499 까지 새 리뷰, 이후 같은 3건 반복
- 정렬 파라미터(`latest` / `oldest` / `low` 등) 유효값을 찾지 못했다
- 연결 리셋이 잦다 — `api()` 가 지수 백오프로 4회 재시도
- 평점 필터로 창을 나눠도 전량은 안 된다:

| 평점 | 보유 | API 도달 가능 |
|---|---|---|
| 1 / 2 / 3 점 | 8 / 2 / 30 | 전부 |
| 4점 | 2,628 | 1,497 |
| 5점 | 24,301 | 1,497 |
| **합계** | **26,969** | **3,034 (11%)** |

→ 과거 이력 89% 는 **엑셀 내보내기 말고 길이 없다.**

### 작성일 처리

**API 응답에 작성일 필드가 없다.** 유일한 실제 날짜 출처는 이관된 네이버페이 구매평의
본문 끝에 박힌 문자열이다(약 13%).

```
잘받았습니다.좋아요.,(2025-09-19 17:40:31 에 등록된 네이버 페이 구매평)
```

`_sync.py` 가 이걸 파싱해 `date` 로 쓰고 `date_estimated: false` 로 표시한다.
못 건진 것은 수집일을 넣되 `date_estimated: true` 이고, **빌더는 추정 날짜를 화면에
표시하지 않는다.** 오래된 후기에 수집일을 붙이면 날짜를 조작한 것처럼 보이기 때문이다.
실제 작성일 전량은 엑셀 내보내기의 `작성일` 컬럼에서 온다.

## 심의 설계 (건강기능식품 표시·광고)

코드에 박혀 있다. 바꾸지 말 것.

1. **전량 게재, 작성 순서대로.** 골라 싣지 않는다 — 선별하면 이용후기가 아니라
   **광고**가 되어 사전심의 대상이 된다
2. **브랜드가 쓴 효능 문장 0줄.** 페이지 텍스트는 고객 원문과 중립 라벨(평점·날짜)뿐
3. **화면에 보이는 리뷰만 `Review` 마크업.** 안 보이는 것을 JSON-LD 에 넣는 것은
   구글 구조화 데이터 정책 위반이고 리치리절트 페널티 대상이다

미인정 기능성 표현(체중·다이어트 / 질병·치료 / 의학적 단정)이 든 리뷰는 **삭제하지
않고 분리**해 `dist/심의검토_대상.csv` 로 뽑는다. 워크플로는 이것을 사이트에서 빼고
Actions 아티팩트로 올린다(30일 보관). **판정은 검수팀이 한다** — 칼륨의 인정 기능성은
나트륨 배출이고 체중감소가 아니다. 1번 원칙과 충돌하는 지점이므로 어느 쪽으로 정하든
근거를 남긴다.

## 최초 1회 설정 (대표님)

1. **GitHub Pages 켜기** — Settings → Pages → Source 를 **GitHub Actions** 로
2. **DNS 에 CNAME 추가** — `review` → `wespotjh.github.io`
   (전용 저장소이므로 `wespotjh.github.io` 자체는 영향받지 않는다)
3. Actions 탭에서 `리뷰 사이트 배포` 워크플로 **Run workflow** 수동 실행

이후엔 매일 04:20(KST)에 자동으로 돈다. `schedule` 은 기본 브랜치(`main`)에서만
발화하므로 이 저장소의 기본 브랜치를 옮기지 말 것.

> Pages 는 무료 플랜에서 **공개 저장소**여야 커스텀 도메인을 붙일 수 있다.
> 이 저장소가 공개인 이유다. 담기는 내용은 이미 공개 페이지에 노출되는 이용후기이고,
> 스토어에는 리뷰 본문·평점·작성일만 들어간다 (주문자 정보는 넣지 않는다).
